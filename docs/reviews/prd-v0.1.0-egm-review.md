## 요약

PRD는 "커스텀 글리프 보호"라는 핵심 약속과 "생성 범위 ≠ 품질 ≠ 검토율" 구분이 명확하고, 비목표·제외 범위도 잘 정리돼 있다. 그러나 구현 착수 전 다음 세 축이 반드시 보강돼야 한다.

1. **글리프 상태 모델:** 어떤 글리프가 실제로 쓰이는지(커스텀 존재 여부 vs `GlyphSelection`), "복원"이 커스텀을 삭제하는지, "관련 글자"가 무엇인지, 재생성 후 검토 상태가 어떻게 되는지가 정의되지 않아 FR-05·FR-06의 인수 조건을 구현자마다 다르게 해석할 수 있다.
2. **TTF 내보내기 계약:** "유효 글리프", 생성 실패 음절 처리, 최소 필수 글리프(`.notdef`, 공백), 폰트 이름·버전, "외부 프로그램"의 구체 목록과 플랫폼별 설치 방식이 없어 FR-08 인수 조건을 검증할 수 없다.
3. **tech-stack.md와의 불일치:** tech-stack.md는 "온디바이스 전용"을 `[확정]`했지만 PRD는 OQ-03에서 서버 빌드를 열어 두고 NFR-04는 "검토" 수준이다.

## 우선순위별 발견 사항 (Blocker → Major → Nit)

### Blocker

#### B-01. 유효 글리프 결정 주체와 "복원" 의미가 정의되지 않음 — 심각도: Blocker
* **리뷰어 관점:** `design`, `implementation-readiness`, `comprehension`, `style`, `zoom-out`, `inventive-catalyst`
* **영향 범위:** 87, 89, 92, 132, 139–141행 (FR-05, §5 `GlyphSelection`, POL-01~03), OQ-06(183행)
* **문제:**
  - 87행은 "커스텀 글리프가 **있으면** 우선 적용"이라 하여 *존재 여부*로 결정하고, 132행 `GlyphSelection`은 *선택값*으로 결정한다. `CustomGlyph`가 있으나 선택이 `generated`인 상태를 어떻게 다루는지 불명확하다.
  - 92행 "명시적으로 복원", 89행 "교체", 141행 "전환"이 같은 동작인지, 이 동작이 커스텀 데이터를 **삭제**하는지 **보존한 채 선택만 바꾸는지** 알 수 없다. POL-01은 *시스템*의 삭제만 금지하므로, 사용자가 한 번 탭으로 수작업을 영구 손실할 수 있다.
  - "복원"은 56·65·113행에서는 "프로젝트 다시 불러오기" 의미로도 쓰여 인수 조건이 이중 해석된다.
  - POL-02·FR-04가 의존하는 "자동 생성 상태"가 `selection == generated`인지 "커스텀 없음"인지 정의되지 않았다.
* **권고:**
  - `GlyphSelection`을 미리보기·내보내기의 **유일한 결정 기준**으로 확정한다. 87행: "음절의 선택 상태가 `custom`이면 커스텀 글리프를 미리보기와 내보내기에 적용한다."
  - 동작을 둘로 분리한다.
    - **자동 생성으로 되돌리기**: `GlyphSelection`만 `generated`로 바꾸며 커스텀 글리프는 보존되고 다시 선택할 수 있다.
    - **커스텀 글리프 삭제**: 확인 단계를 거치는 별도 파괴적 동작이며, 커스텀 데이터를 제거하는 유일한 경로다. (90행 `[제안]` → `[확정]`)
  - 불변식을 명시한다: `selection == custom ⇒ CustomGlyph 존재`, 커스텀은 미선택 상태로 존재할 수 있음, "자동 생성 상태 = `selection == generated`".
  - 92행 문구: "사용자가 `강`을 명시적으로 **자동 생성으로 되돌린** 이후에만 자동 생성 결과를 따른다. 되돌린 후에도 커스텀 `강`은 보존되어 다시 선택할 수 있다."
  - "복원"은 프로젝트 불러오기 의미로만 쓰고, 141·183행도 "되돌리기"로 통일한다.
  - §5는 `[제안]`으로 두되, 최소 상태·전이 표(상태 × 이벤트 → 결과 선택값·검토 상태·확인 여부)를 `[확정]`으로 FR-05에 추가한다. 이벤트 예: 기본 글리프 수정, 재생성, 커스텀 작성, 되돌리기, 커스텀 재선택, 커스텀 삭제.

#### B-02. "영향을 받는/관련 글자"의 범위와 재생성 트리거가 모순·미정의 — 심각도: Blocker
* **리뷰어 관점:** `comprehension`, `implementation-readiness`, `design`, `style`, `zoom-out`, `inventive-catalyst`
* **영향 범위:** 43, 78, 88, 92, 140행
* **문제:**
  - "영향을 받는 자동 생성 상태 글자"(78), "다른 자동 생성 상태의 관련 글자"(92), "자동 생성 상태의 관련 글자"(140) 세 표현이 혼재하며 기준이 없다. `ㄱ` 수정 시 초성 `ㄱ`만인지, 받침 `ㄱ`·`ㄲ`·`ㄳ`까지인지 판단할 수 없다.
  - 78행은 변경이 자동 반영되는 것처럼 읽히고, 43·92행은 사용자가 "전체 자동 생성"을 실행하는 것을 전제한다. 자동/수동 트리거가 정해지지 않았다.
  - `GeneratedGlyph`(130행)에 입력 기본 글리프 버전이 없어 최신 여부(stale)를 판별할 수 없다.
* **권고:**
  - POL-02를 단일 정의로 고친다: "**POL-02 [확정]** 기본 글리프 변경은 해당 기본 글리프를 조합에 사용하는 음절 중 선택 상태가 `generated`인 음절에만 반영한다." FR-04·FR-05는 "POL-02를 따른다"로 참조한다.
  - 재생성 트리거를 결정한다(예: "기본 글리프 저장 시 영향 음절을 자동 재생성하고, '전체 재생성'은 유지보수용 명시 동작으로 둔다").
  - 간단안(zoom-out): 생성이 결정적(deterministic)이라면 의존성 추적 없이 "`generated` 선택 음절 전체 재생성"으로 정의해도 결과는 같다. 성능 문제는 G0에서 증분 재생성과 비교 측정한다.
  - `GeneratedGlyph`에 입력 기본 글리프 ID·버전을 기록한다는 `[제안]`을 §5에 추가한다.

#### B-03. 재생성 후 검토 상태가 갱신되지 않아 가중 검토율이 과대 표시됨 + 산식 부재 — 심각도: Blocker
* **리뷰어 관점:** `design`, `inventive-catalyst`, `implementation-readiness`, `comprehension`
* **영향 범위:** 98–104, 133행 (FR-06, `ReviewState`), OQ-05(182행)
* **문제:**
  - `ReviewState`는 검토 상태와 중요도 데이터 버전만 저장한다. 기본 `ㄱ`을 고치면 `ㄱ`을 쓰는 "검토 완료" 음절의 모양이 바뀌어도 상태가 유지되어, 99·102행의 의도(검토율이 실제 진행을 반영)가 깨진다.
  - "가중 검토율"의 산식, "검토 완료"로 표시하는 사용자 동작, 커스텀 전환 시 검토 상태 처리가 모두 없어 102행 인수 조건을 검증할 수 없다.
* **권고:**
  - `ReviewState`에 "검토한 글리프의 식별자(소스 + 생성/수정 버전 또는 해시)"를 저장하고, 현재 유효 글리프 식별자와 다르면 "재검토 필요"로 전환한다.
  - FR-06 인수 조건 추가: "기본 `ㄱ`을 수정하면, `ㄱ`을 사용하는 자동 생성 음절 중 검토 완료였던 음절은 재검토 필요 상태가 된다. 커스텀 음절의 검토 상태는 바뀌지 않는다."
  - 잠정 산식: "가중 검토율 = Σ(검토 완료 음절의 가중치) / Σ(전체 음절 가중치)".
  - "검토 완료"의 정의(예: 사용자가 검토 화면에서 '확인' 동작을 수행한 상태)를 `[제안]`으로라도 기재한다.
  - 중요도 데이터 버전은 음절별이 아니라 프로젝트 단위로 둔다(Nit N-04 참조).

#### B-04. TTF 내보내기 시 "유효 글리프"와 생성 실패 음절 처리가 미정의 — 심각도: Blocker
* **리뷰어 관점:** `implementation-readiness`, `design`, `comprehension`, `inventive-catalyst`, `codebase-details`
* **영향 범위:** 80, 117, 120, 122, 130, 143행
* **문제:** FR-04는 음절별 오류 상태를 허용(80행)하지만, FR-08은 "선택된 유효 글리프"(117행)만 내보낸다고 할 뿐 오류 음절을 (a) cmap에서 제외(외부 앱이 대체 폰트 표시), (b) `.notdef`/빈 글리프로 매핑(두부 상자), (c) 내보내기 차단 중 무엇으로 처리할지 정하지 않았다. 122행 인수 조건을 검증할 수 없다.
* **권고:**
  - "유효 글리프"를 정의한다: "선택 상태의 소스가 존재하고 오류 상태가 아닌 글리프".
  - 정책 예시(`[제안]`): "오류 음절은 cmap에서 제외해 외부 프로그램의 대체 폰트로 표시되게 한다. 내보내기 전 제외 음절 수와 목록(중요도 순)을 사용자에게 보여 준다. 제외 음절의 중요도 가중 비율이 G0에서 정한 임계값을 넘으면 내보내기 전에 경고한다."
  - FR-08 인수 조건 추가: "오류 상태 음절이 있어도 내보내기가 완료되며, 제외 음절 목록이 사용자에게 표시된다."

#### B-05. 실사용 가능한 TTF의 최소 글리프·폰트 메타데이터·재내보내기 식별 규칙 부재 — 심각도: Blocker
* **리뷰어 관점:** `implementation-readiness`, `design`, `codebase-details`, `zoom-out`
* **영향 범위:** 111, 117–122, 126–133행, OQ-04(181행), 재방문 흐름(45행)
* **문제:**
  - `.notdef`와 공백(U+0020)이 없으면 "실제 타이핑"이 성립하지 않는데, 영문·숫자·기호와 함께 OQ-04로 전부 미결정이다.
  - `ㅋㅋ`, `ㅠㅠ` 같은 낱자 입력은 호환 자모(U+3131–U+318E)로 입력되어 U+AC00–U+D7A3 범위 밖이다. 일상 문장에서 122행 인수 조건이 실패할 수 있다.
  - family name(한글 프로젝트명의 ASCII 대체 포함), 버전, UPM, ascender/descender, advance width 등을 둘 데이터 개념이 없다. 같은 이름으로 재내보내면 OS 폰트 캐시가 이전 버전을 계속 쓰거나 설치를 거부할 수 있다.
* **권고:**
  - FR-08에 `[확정]` 최소 글리프 세트를 둔다: "`.notdef`, U+0020(공백). 호환 자모 U+3131–U+3163의 포함 여부는 G1에서 결정한다(사용자가 이미 자모를 작성하므로 비용이 낮다)." 영문·숫자·기호는 OQ-04에 남긴다.
  - §5에 `FontMetadata`(family/style 이름, ASCII 대체 이름, 버전, UPM, 수직 메트릭, 라이선스 문구) 개념을 추가한다.
  - FR-08에 "내보낼 때마다 폰트 버전(또는 고유 ID)이 증가한다"는 규칙을 추가한다.

#### B-06. "외부 (지원) 프로그램"과 플랫폼별 설치 경로가 정의되지 않아 핵심 인수 조건 검증 불가 — 심각도: Blocker
* **리뷰어 관점:** `implementation-readiness`, `zoom-out`, `codebase-details`, `comprehension`, `style`
* **영향 범위:** 32, 43, 118–122, 170, 172, 181행
* **문제:**
  - "실제 외부 프로그램"(32), "다른 프로그램"(43), "외부의 지원 프로그램"(119), "외부 앱"(181)이 혼용되며 목록이 없다.

* **권고:**
  - 용어를 "외부 프로그램"으로 통일하고 119행을 다음처럼 바꾼다: "생성 파일은 **지원 대상 외부 프로그램(목록: OQ-09)**에서 설치·선택·입력할 수 있어야 한다."

  - iOS 앱 내 폰트 등록을 범위에 넣을지를 `[미결정]`으로 명시한다.
