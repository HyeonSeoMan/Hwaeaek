**판정: Spec 갱신 전에 부분 수정이 필요하다.** 다듬기 단계의 구조와 점검 상태 개념은 기존 불변식과 맞는다. 선택 상태가 유일한 기준이라는 점, 자동 생성 결과를 저장하지 않는다는 점, POL-01~03과도 충돌하지 않는다. "지문만 저장하고 다시 확인 필요는 계산한다"는 방식도 v0.3에서 문제였던 대량 행 갱신을 피한다. 하지만 그 지문이 무엇인지, 단계 완료가 무엇인지, "이전 모양으로 되돌리기"가 어떻게 일어나는지가 정의되지 않았다. 그래서 Spec 작성자가 이 세 가지를 추측해야 한다. 리뷰어 8명 중 6명 이상이 같은 지점을 따로 짚었다.

문제는 세 곳에 몰려 있다.

1. **점검 상태의 정의가 비어 있다.** 지문 입력, 완료 판정, 되돌리기 수단, 커스텀 전환 시의 기록 처리가 정해지지 않았다(B-1, B-2, B-3, R-7, R-8).
2. **단계 경계와 데이터 출처가 정해지지 않았다.** 7·8단계 경계, KS X 1001과의 관계, 묶음 안 순서가 비어 있다. 빈도 데이터는 저장소에 없다(R-2, R-3).
3. **51자 변경이 기존 규칙과 덜 맞춰졌다.** 2단계 전 점검 단계 열기, 기존 35자 프로젝트의 메모·내보내기, 저장·백업 목록, "보강"이라는 용어가 서로 맞지 않는다(R-4, R-5, R-6, R-10).

검증된 사실(지적 없음)은 다음과 같다.
- 152행 "6,762자"는 맞다. 계산은 2,940(쌍자음 초성 5 × 588) + 3,822(일반 초성 14 × 중성 21 × 종성 13)다. 종성 `ㄲ`·`ㅆ`를 셌다.
- 16자 목록은 `hangul.dart:30-47`의 `compoundConsonants`와 같다.
- "기본 문장부호 26자"는 `latin_set.dart:12-16`과 같다.
- 154행의 구성 자음 대체는 `composer.dart:238-251`(`_placeParts`)와 같다.
- 167행·TS-20의 "메모는 다시 잠그지 않는다"는 `glyph_dao.dart:91-100`의 한 번만 기록하는 `memo_unlocked_at`와 같다.

## 1. Spec 갱신 전에 고칠 것

### B-1. 지문의 입력이 정의되지 않았고, 기존 의존 함수를 그대로 쓰면 결과가 틀린다 — 차단
- **리뷰어:** design, implementation-readiness, codebase-details, inventive-catalyst, comprehension, zoom-out, structural
- **위치:** 46행(용어), 171행(OQ-01 의존 함수 `[미결정]`), 252행, 362행(§5 `GlyphReview`), 379행(POL-09), 380·511행(POL-08·OQ-12), 168행(기기 간 ±1 허용)
- **문제:**
  - 252행은 "의존하는 기본 글리프의 모양"을, 362행은 "의존 기본 글리프 지문(모양 해시)"을 기록한다고만 쓴다. 다음이 정해지지 않았다.
    - **해시 대상.** 원본 획 데이터 전체를 쓰는가(시간·필압·기울기 포함), 일부 필드만 쓰는가, 계산된 윤곽선을 쓰는가. 윤곽선을 쓰면 168행이 허용한 기기 간 ±1 차이 때문에 백업을 다른 기기에서 가져올 때 모든 확인함이 다시 확인 필요로 바뀐다.
    - **의존 집합.** 음절 → 의존 기본 글리프 함수는 아직 `[미결정]`(171행, OQ-01, G1 차단)인데, 이 함수에 기대는 FR-06 동작은 `[확정]`이다. FR-06 관련 줄(222행)에도 OQ-01이 없다.
    - **실제 코드의 의존 함수.** `HangulComposer.dependencies`(`composer.dart:162-186`)는 쌍자음·겹받침 자리에 겹자모 키와 구성 자음 키를 **모두** 넣는다. `ㄲ`이면 {ㄲ, ㄱ}, `ㄺ`이면 {ㄺ, ㄹ, ㄱ}이다. 필수 51자가 모두 있으면 조합기는 구성 자음을 쓰지 않는다(`_placeParts`, `:241-242`). 이 함수로 지문을 만들면 `ㄱ`만 고쳐도 `까`·`닭` 등 쌍자음·겹받침 음절이 잘못 다시 확인 필요가 된다. 그런 음절은 최대 6,762자다.
    - **배치 변화.** 겹받침 글리프가 비면 `_raiseTail`이 받침 자리를 옮긴다(`:213-217`). "어떤 글리프가 없음"은 획 해시만으로는 표현되지 않는다.
    - **조합 규칙 버전.** 규칙 업데이트(POL-08·OQ-12)는 기본 글리프를 바꾸지 않고 자동 생성 모양을 바꾼다. 지문에 규칙 버전이 없으면 확인함이 사용자가 보지 않은 모양에 남는다. 반대로 `ruleVersion`을 그대로 넣으면, 모양이 거의 그대로인 변경에도 11,172자가 모두 뒤집힌다. 곡선 맞춤으로 2로 올린 변경이 그런 예다.
  - 46행 용어 정의는 다시 확인 필요를 "기본 글리프가 바뀜"이라는 사건으로 정의한다. 252행과 POL-09는 이를 비교로 계산한다. 두 정의가 다르다.
- **수정:**
  - FR-06 또는 §5에 지문을 정의한다. 예시 문장을 둔다.
    > 지문은 조합 엔진이 그 음절을 만들 때 **실제로 쓴** 기본 글리프마다 (역할 키, 저장된 원본 획 데이터의 바이트 해시)를 역할 키 순서로 모은 것이다. 겹자모를 구성 자음으로 만든 경우 구성 자음과 "겹자모 없음"을 함께 기록한다. 해시는 플랫폼과 무관한 고정 알고리즘(예: SHA-256)으로 계산하며, 윤곽선에서 계산하지 않는다.
  - 의존 함수 중 "실제로 쓴 입력" 부분은 OQ-01에서 꺼내 FR-06에서 확정한다. 코드는 `dependencies()`를 캐시 무효화용 보수 집합으로 남기고, 지문용으로 `resolvedDependencies(cp, present)`를 따로 둔다.
  - 조합 규칙 버전 처리를 POL-09에 한 줄로 적는다. 권장안은 이렇다. 모양이 보이게 바뀌는 변경에만 올리는 "모양 규칙 버전"을 지문에 넣는다. 적용 시점은 OQ-12에 연결한다.
  - 46행을 "의존 기본 글리프의 현재 지문이 확인할 때와 다름"으로 고친다. 222행에 OQ-01, 500행 관련 칸에 FR-06을 추가한다.
  - TS를 추가한다. `ㄲ`을 쓴 상태에서 `깡`을 확인함으로 표시하고 `ㄱ`을 수정하면 `깡`은 확인함으로 남는다. `ㄲ`을 비우면 `깡`은 다시 확인 필요가 된다.

### B-2. 점검 단계 "완료"의 정의가 서로 모순된다 — 차단
- **리뷰어:** comprehension(차단), structural, implementation-readiness, design, zoom-out, inventive-catalyst
- **위치:** 46행, 68행(단계 진행), 69행(현재 단계), 249행, 254행, 255행, 482행(TS-24)
- **문제:**
  - 249행은 단계 완료를 "모든 음절이 직접 그림 또는 확인함"으로 정의한다. 46행은 다시 확인 필요를 확인함과 다른 상태로 둔다. 그러면 음절 하나가 다시 확인 필요가 되는 순간 249행 기준으로 단계는 미완료다.
  - 254행과 TS-24는 이때 완료 표시를 유지하라고 한다. 이를 지키려면 완료를 저장된 표시로 두어야 하는데, §5에 그런 필드가 없다.
  - 68행 진행의 분자에 다시 확인 필요를 세는지가 없다. 100 / 100이 99 / 100으로 떨어지는지 알 수 없다.
  - 현재 단계(69·255행)가 이 단계를 완료로 보는지 미완료로 보는지에 따라, `ㄱ` 하나를 고친 뒤 현재 단계가 7단계로 돌아가는지가 갈린다.
  - 완료를 저장한다면 무엇이 그 표시를 지우는지도 없다. 확인함 해제(251행), 자동 생성으로 되돌리기, 업데이트로 단계 구성 변경이 후보다.
- **수정:** 완료를 저장하지 않고 계산하는 모델을 권한다(리뷰어 5명이 같은 안을 냈다).
  - 점검 단계의 음절은 커스텀이거나 확인 기록이 있으면 "처리됨"으로 센다. 기록의 지문이 지금과 맞는지는 따지지 않는다. 다시 확인 필요 수는 따로 표시한다.
  - 68행: "점검 단계는 직접 그림 음절과 확인 기록이 있는 음절(다시 확인 필요 포함)을 센다."
  - 249행을 같은 기준으로 고치고, 254행의 "완료 표시는 유지하고"는 지운다. 이 규칙에서 저절로 따라 나온다.
  - 확인함 해제나 자동 생성으로 되돌리기로 미확인 음절이 생기면 그 단계는 미완료라고 적는다.
  - TS-24를 고치고, 기본 글리프를 고친 뒤 현재 단계가 그대로인지 확인하는 TS를 추가한다.

### B-3. "이전 모양으로 되돌리면 확인함"과 "이전·이후 모양 비교"에 필요한 데이터와 동작이 없다 — 차단
- **리뷰어:** implementation-readiness(차단), inventive-catalyst(차단), codebase-details, design, zoom-out, comprehension, structural
- **위치:** 252행, 256행, 265행, 480행(TS-22), 142행(편집 화면 Undo는 화면을 벗어나면 사라짐), 359행(`BaseGlyph` 이력 없음), 362행
- **문제:**
  - 기본 글리프는 이력이 없다. `glyph_dao.dart:78-87`은 `base_glyphs` 행 하나를 `insertOnConflictUpdate`로 덮어쓴다. 편집 화면 Undo는 화면을 나가면 사라진다(142행). 따라서 저장하고 나간 뒤에는 이전 획으로 돌아갈 방법이 없다. 손으로 다시 그린 획이 해시와 같아지는 일도 없다.
  - 265행 인수 조건 후반과 TS-22의 "되돌림"은 UI로 만들 수 없다. 테스트에서 같은 바이트를 넣어야만 통과한다.
  - 256행은 "이전·이후 모양 비교"를 요구한다. 그러나 `GlyphReview`는 해시만 저장하므로 이전 모양을 그릴 데이터가 없다.
- **수정:** 다음 중 하나를 고른다.
  - (a) **기본 글리프 버전 보관.** 기본 글리프를 저장할 때마다 이전 획을 해시로 찾을 수 있게 보관한다. 지문은 그 버전을 가리킨다. "기본 글리프 이전 모양으로 되돌리기"를 이름 있는 동작으로 FR-03에 추가한다. 비교 화면은 지문이 가리키는 버전을 그린다. §5에 보관 필드를, FR-09에 백업 대상을 추가하고, 정리 규칙(참조 없는 오래된 버전 삭제)을 둔다.

### R-1. "작성"이 정의되지 않았고, 획마다 하는 자동 저장과 "기본 글리프 저장"이 구분되지 않는다 — 주요

### R-2. 7·8·10·11단계의 구성을 문서만으로 정할 수 없다 — 주요
- **리뷰어:** comprehension, implementation-readiness, structural, design, inventive-catalyst, codebase-details, style
- **위치:** 47행, 236~242행, 250행, 254행(예시 `64 / 100`)
- **문제:**
  - 47행은 "묶음 안의 순서는 빈도가 아니다"라고 쓴다. 그러면 "빈도 상위 약 100·500자"는 "앞쪽 묶음 k개"만 뜻할 수 있다. 묶음 크기가 평균 약 71자(1,426 / 20)라 "약 100"은 71이 될 수도, 142가 될 수도 있다. 묶음 번호가 빈도 순위를 따르는지도 문서에 없다.
  - 242행은 정확한 수를 Spec에 넘긴다. 이 내용이 `[확정]` 제목 아래 OQ 없이 있어 §0 20행 규칙과 맞지 않는다. 254행 예시는 정확히 100자를 암시한다.
  - 10단계 "KS X 1001 2,350자까지"와 11단계 "약 8,800자"는 빈도 묶음 1,426자가 모두 KS X 1001 안에 있을 때만 맞는다. 웹 빈도 묶음에는 KS X 1001 밖 음절(예: `됬`)이 있을 수 있다.
  - 빈도 묶음 파일의 한글 외 문자를 걸러 내는지, 묶음 안에서 어떤 순서로 보여 주는지(250행)가 없다.
- **수정:** 집합으로 정의한다.
  - S7 = 빈도 묶음 1..k7의 한글 음절(`U+AC00`~`U+D7A3`). k7은 누적 음절 수가 처음으로 100 이상이 되는 묶음이다.
  - S8은 같은 방식으로 500 이상이다. S9 = 묶음 1~20의 한글 음절, S10 = S9 ∪ KS X 1001 한글, S11 = 11,172자 전체다.
  - n단계 = Sn − S(n−1). 한글이 아닌 코드포인트는 버린다.
  - 표시 순서는 묶음 번호, 묶음 안에서는 Unicode 순서로 한다. 10·11단계는 Unicode 순서로 한다.
  - Spec이 실제 데이터에서 계산한 k7·k8과 단계별 글자 수를 기록한다. 고정된 데이터로 단계 크기를 확인하는 TS를 추가한다.
  - 254행 예시는 `64 / N` 꼴로 바꾸거나, 실제 크기가 정해진 뒤 고친다. 표의 "약 100·500자"는 근사값이라고 적는다.

### R-7. 커스텀 전환, 삭제, 재확인, 해제, 조합 오류 시 점검 기록이 어떻게 되는지 없다 — 주요
- **리뷰어:** design, implementation-readiness, inventive-catalyst, structural, comprehension, codebase-details
- **위치:** 46행, 199~212행(FR-05 상태 전이), 249~253행, 362행, 379행(POL-09)
- **문제:**
  - **되살아나는 확인함.** 확인함 `강`을 커스텀으로 다시 그린 뒤 자동 생성으로 되돌리면(또는 커스텀 글리프를 삭제하면) 이전 기록이 남는지 없다. 남는다면 지문이 맞을 때 `강`은 확인함으로 돌아온다. 그런데 사용자는 그 자동 생성 모양이 싫어서 다시 그렸던 것이다. POL-09는 기본 글리프 변경 때 기록을 지우지 말라고만 할 뿐, 선택 상태가 바뀔 때는 말하지 않는다.
  - **재확인.** 다시 확인 필요 음절을 다시 확인하면 지문을 새로 쓰는지 없다. 새로 쓰면 이전 모양으로 되돌렸을 때 확인함이 되는 규칙(252행)과 부딪친다.
  - **해제.** 해제(251행)가 기록을 지우는지, 해제한 음절이 미확인이 되는지 없다.
  - **조합 오류.** 조합 오류 음절을 확인함으로 표시할 수 있는지 없다. 249행은 셀 수 없다고만 암시한다. 확인함 음절이 나중에 조합 오류가 되면 어떻게 셀지도 없다.
  - **실행 취소.** 점검 실행 취소가 FR-05 실행 취소와 같은 기록인지 따로인지 없다.
- **수정:**
  - FR-06에 점검 기록 상태 전이 표를 둔다. 열은 FR-05와 같은 형식으로 하고, 이벤트는 확인, 해제, 재확인, 커스텀 저장, 자동 생성으로 되돌리기, 커스텀 삭제, 기본 글리프 변경, 실행 취소로 한다. 또는 FR-05 표에 "점검 기록" 열을 추가한다.
  - 커스텀 전환 시의 처리를 고른다(사용자 결정).
    - (a) 커스텀 저장 때 같은 트랜잭션(128행)에서 기록을 지우고, 실행 취소 때 함께 되살린다(inventive-catalyst 권장).
    - (b) 기록은 선택 상태와 독립으로 남기고, 선택 상태가 `generated`일 때만 평가한다(design 권장).
  - 확인함 표시는 조합에 성공한 자동 생성 음절에만 허용한다. 조합 오류 음절은 점검 상태와 관계없이 미완료로 센다.
  - 해제하면 기록을 지우고 미확인이 된다. 재확인하면 지문을 현재 값으로 바꾼다.
  - 커스텀 → 되돌리기 왕복을 확인하는 TS를 추가한다(중간에 기본 글리프를 바꾼 경우와 바꾸지 않은 경우).

### R-8. 일괄 "이대로 좋음"의 범위가 기기마다 다르고, 실행 취소 결과가 틀리게 적혀 있다 — 주요
- **리뷰어:** implementation-readiness, structural, design, comprehension, zoom-out, inventive-catalyst
- **위치:** 250행, 481행(TS-23)
- **문제:**
  - "화면에 보이는 음절 전체"는 기기 크기, 글자 크기, 스크롤 위치에 따라 달라진다. 그래서 TS-23이 고정된 집합을 확인할 수 없다.
  - 일괄 표시가 커스텀 음절, 조합 오류 음절, 이미 확인함인 음절, 다시 확인 필요 음절을 건너뛰는지 없다.
  - TS-23은 실행 취소 후 "모두 미확인"을 기대한다. 표시 전에 확인함이나 다시 확인 필요였던 음절에는 틀린 결과다. 다시 확인 필요 음절의 이전 지문을 잃으면 B-3의 되돌리기 경로도 깨진다.
  - 표시 시간은 OQ-06과 연결되어 있지 않다.
- **수정:**
  - 범위를 고정된 단위로 정한다. 후보는 현재 단계의 빈도 묶음 하나, Spec이 정하는 N개 페이지, 단계 전체다(사용자 결정). 대상은 그 단위 안의 조합 성공 자동 생성 음절 중 미확인과 다시 확인 필요다.
  - 일괄 표시는 트랜잭션 하나로 한다. 실행 취소는 영향받은 음절마다 이전 기록(없음 또는 이전 지문)을 그대로 되살린다.
  - TS-23의 Given에 미확인과 다시 확인 필요를 섞고, Then을 "각 음절이 표시 직전 점검 상태로 돌아감"으로 고친다. 250행 실행 취소 표시 시간은 OQ-06을 따른다고 적는다.

### R-9. 선택 항목인 3~6단계 때문에 현재 단계가 멈추고, 모두 완료한 뒤의 표시가 없다 — 주요
- **리뷰어:** zoom-out, inventive-catalyst, comprehension, structural
- **위치:** 36행, 155행, 247행, 255행, 301행, 483행(TS-25)
- **문제:**
  - 숫자·영문·문장부호는 선택이다. 메모 조건이 아니고, 그리지 않아도 제외 목록에 넣지 않는다(301행). 그런데 현재 단계는 "처음으로 완료되지 않은 단계"다. 그래서 한글만 원하는 사용자는 7~11단계를 다 끝내도 `3 / 11단계 · 숫자 0 / 10`에 계속 머문다.
  - 단계 순서는 확정된 결정이지만, 현재 단계 정의와 선택 항목이 함께 쓰일 때 생기는 이 결과는 문서에 없다.
  - 11단계를 모두 끝냈을 때 현재 단계를 어떻게 표시하는지도 없다.
- **수정:** 셋 중 하나를 고른다(사용자 결정).
  - (a) 이 동작을 의도로 명시한다.
  - (b) 3~6단계에 되돌릴 수 있는 "이 단계 건너뛰기"를 둔다. 현재 단계는 완료되지도 건너뛰지도 않은 첫 단계가 되고, 단계 지도에는 "건너뜀"으로 표시한다.
  - (c) 현재 단계 표시를 `[제안]`으로 내리고 단계 지도만 확정한다.
  - 어느 쪽이든 "모두 완료 시 `11 / 11단계 완료` 표시" 한 줄을 추가하고, TS-25에 해당 경우를 넣는다.

### R-10. "보강"이 필수와 선택 두 뜻으로 쓰인다 — 주요
- **리뷰어:** style, codebase-details, implementation-readiness
- **위치:** 38행("선택 **보강 기본 글리프**(자모 변형 등, OQ-01)"), 152행·231행(2단계 "보강 자모" 16자 = 필수), 500행(OQ-01 "필수·보강 기본 글리프 구성")
- **문제:** 같은 "보강"이 필수 16자와 앞으로 생길 선택 자모 변형을 함께 가리킨다. 코드는 38행 뜻을 따른다. `base_set.dart:22-26`의 `supplementaryBaseGlyphs`가 16자이고, `base_glyph_screen.dart:167`이 "보강 (선택)"으로 표시한다. 그래서 이름만 보고 구현하면 16자가 계속 선택으로 남는다.
- **수정:**

  - 코드 영향: `latestBaseSetVersion = 2`, `requiredBaseGlyphs(2)` = 35자 + 16자(1단계 → 2단계 순서), `supplementaryBaseGlyphs(2)` = 빈 목록, "(선택)" 표시 제거.

### R-11. FR-03 `[확정]` 51자 구성과 OQ-01 `[미결정]`의 범위가 겹친다 — 주요
- **리뷰어:** comprehension, style

### R-12. `ㄱ`(초성) 표기와 위치 구분 없는 기본 글리프가 맞지 않아 TS 기대 결과가 틀린다 — 주요

### R-13. 새로 확정한 항목 중 인수 조건이나 TS가 없는 것이 많다 — 주요 (나중에 수정 가능)

## 부록 A. 확정된 결정에 대한 의견 (다시 논의 대상 아님)

리뷰어가 낸 의견을 기록만 한다. 위 지적의 판정에는 반영하지 않았다.

- **10·11단계의 크기**(zoom-out). 10단계 약 924자와 11단계 약 8,800자를 끝낼 사용자는 적을 것이다. 진행 신호는 대부분 1~9단계에서 나온다. 10·11단계를 "내보내기에는 이미 포함됨"으로 보여 주는 편이 GOAL-04에 더 맞을 수 있다는 의견이다.
- **3~6단계를 한글 점검 앞에 둔 순서**(zoom-out, inventive-catalyst). RISK-02가 기대는 한글 점검이 늦어진다는 의견이다. R-9를 해결하면 이 부담이 줄어든다.
- **필수 51자와 SM-01**(inventive-catalyst). 첫 메모까지 걸리는 시간이 35자 때보다 길어진다. 다시 논의할 일이 아니라 G0 측정에서 알려진 비용으로 기록하면 된다.

## 부록 B. 선택 개선안 (inventive-catalyst)

지적이 아니라, 확정된 결정을 유지하면서 생각해 볼 만한 설계안이다.

- **역할별 지문과 부분 재승인.** 지문을 "역할 → 기본 글리프 버전 해시" 맵으로 저장한다(B-1). 기본 글리프를 고친 뒤 그 역할에 영향받는 음절만 배치 유형별로 몇 개씩 이전·이후 격자로 보여 준다. 사용자가 받아들이면 선택된 기록의 해당 역할 해시만 바꾼다. 흔한 자모(`ㅇ`, `ㅏ`)를 고칠 때 점검 진행이 수천 자씩 뒤집혀 사용자가 기본 글리프 개선을 피하게 되는 문제를 줄인다. B-3 (a)안이 필요하다.
- **"좋은 것 표시"에서 "나쁜 것 표시"로.** 고정 페이지 N자 단위로 보여 주고, "이 페이지 좋음"은 사용자가 다시 그리기나 표시를 하지 않은 음절만 확인함으로 만든다. 페이지가 실제로 표시된 뒤에만 누를 수 있게 한다. 확인 방식(`single`/`page`)을 기록에 남기면 나중에 기기 안에서 분석할 수 있다. R-8의 범위 결정과 함께 검토한다.
- **기본 글리프 초안과 확정 분리.** 이미 코드에 있는 구분(`drafts` / `saveBaseGlyph`)을 PRD 수준에서 명시한다. 그러면 R-1과 B-3이 함께 단순해진다.
