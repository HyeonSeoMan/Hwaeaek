## 차단 (Blocker)

### B-1. 획 좌표 정밀도가 메모리(double)와 DB(f32)에서 달라 앱 표시와 TTF가 갈라진다
- **리뷰어:** design, implementation-readiness, inventive-catalyst
- **위치:** §3.1 81행, §4.2 181행, §7.2 315~316행
- **문제:** `InkPoint`는 `double`, HWS1은 `f32`다. 저장 직후 조합 캐시와 메모 폰트는 메모리의 double로 만들고, 내보내기는 DB에서 읽은 f32로 스냅샷을 만든다. `perfect_freehand` → Douglas–Peucker → 정수 반올림을 거치면 두 입력의 윤곽선이 다를 수 있다. 그러면 FR-04 "앱 안 표시 = TTF", TS-12, FR-02 인수 조건("원본 획 데이터가 저장 전과 일치")이 깨진다. 앱을 다시 열면 모양이 바뀌는 현상으로도 나타난다.
- **수정:** 둘 중 하나를 §3.1에 못 박는다.
  - (권장) 획이 끝나는 즉시 점을 f32로 양자화한다(`Float32List` 왕복). 도메인은 DB가 표현할 수 없는 값을 갖지 않는다.
  - 또는 HWS1을 x·y·pressure `f64`로 바꾼다.
  - §12에 "새로 그린 획과 HWS1 왕복 후 획의 `compose` 결과가 같다" 테스트를 추가한다.

### B-2. 쓰기 실패와 재시도의 의미가 정해지지 않았다
- **리뷰어:** implementation-readiness, design, inventive-catalyst
- **위치:** §4.3 209행
- **문제:** "메모리에 유지 + 지수 백오프 재시도" 한 줄뿐이다. 다음을 정하지 않아 FR-01, POL-03, POL-05, TS-16을 구현·검증할 수 없다.
  - 쓰기 큐가 하나인지, 직렬인지. 실패한 쓰기 뒤의 쓰기가 앞질러 성공하면 재시도가 새 상태를 덮어쓴다(선택 상태 순서 역전, POL-03).
  - 화면·메모 폰트·빈도순 목록이 메모리 상태를 보여 주는지 DB 스냅샷을 보여 주는지. 메모리를 보이면 내보내기(DB 읽기)가 화면과 다른 TTF를 만들고(FR-08), DB를 보이면 사용자가 방금 한 수정이 보이지 않는다.
  - 커스텀 저장 insert가 실패하면 `custom_revisions.id`가 없어 실행 취소 항목이 가리킬 대상이 없다.
  - 재시도가 끝나는지, 디스크 가득(`SQLITE_FULL`) 때 사용자에게 무엇을 안내하는지, 앱 종료 시 큐는 어떻게 되는지.
  - 저장 확인 전에 편집 화면을 닫을 수 있는지.
- **수정:** §4.3에 다음을 추가한다.
  - DB당 직렬 `WriteQueue` 하나. FIFO, 실패한 항목 뒤의 쓰기는 앞지르지 않는다. 같은 `(project, code_point)`·같은 메모의 연속 갱신은 마지막 값으로 합친다.
  - 화면 기준 = 커밋된 DB 스냅샷 + 대기 중 작업을 순서대로 덧씌운 것. 큐가 비어 있지 않으면 내보내기를 시작하지 않는다(또는 비워질 때까지 기다린다).
  - 글리프 저장은 커밋될 때까지 편집 화면과 획을 유지하고, 실패하면 "다시 시도" 배너를 띄운다. 초안(§4.4)이 강제 종료 대비책이다.
  - 연속 3회 실패 또는 `SQLITE_FULL`이면 "저장 공간 확보 / 백업 내보내기" 안내로 바꾼다.
  - 아직 저장되지 않은 작업의 실행 취소는 DB update가 아니라 큐에서 제거한다.

### B-3. 실행 취소가 이미 바뀐 상태에 적용될 수 있다
- **리뷰어:** implementation-readiness, design
- **위치:** §9.1 377~381행
- **문제:** 슬롯은 동작 직전 값만 보관한다. 5초 안에 같은 음절의 커스텀 글리프를 삭제하면, 실행 취소가 없어진 `current_revision_id`를 써서 FK 오류가 나거나(FK가 꺼져 있으면) 불변식이 깨진다. 같은 음절·다른 음절에 두 번째 동작을 하거나, 프로젝트를 바꾸거나, 원래 쓰기가 아직 대기 중일 때(B-2)의 동작도 정의되어 있지 않다.
- **수정:** 슬롯에 `before`와 `after`를 모두 둔다. 실행 취소는 한 트랜잭션에서 비교 후 교체(`UPDATE … WHERE selection = :after.selection AND current_revision_id = :after.rev`)로 하고, 영향 행이 0이면 "되돌릴 수 없습니다"를 표시한다. 커스텀 글리프 삭제, 프로젝트 전환·삭제, 스낵바 닫힘 때 슬롯을 비운다. 새 동작은 슬롯을 교체한다. 테스트: "커스텀 저장 → 삭제 → 실행 취소"가 아무것도 바꾸지 않는다.

### B-4. 백업 형식이 구현할 수 있을 만큼 정의되지 않았고, 복원이 손실된다
- **리뷰어:** implementation-readiness, comprehension, design, zoom-out
- **위치:** §11.1 424~432행
- **문제:**
  - `manifest.project`가 "…메타데이터"뿐이고, `custom/index.json` 스키마가 없다.
  - `custom/<코드포인트>`가 10진인지 16진인지 없다(`base_glyphs/`는 16진).
  - "수정본 순번"과 `custom_revisions.id`(전역 AUTOINCREMENT)의 대응이 없다.
  - 수정본 `createdAt`이 들어갈 자리가 없어 이력 날짜가 복원되지 않는다. FR-09 인수 조건("수정 이력 … 복원")을 엄밀히 만족하지 못한다.
  - 소프트 삭제 메모, 초안을 포함하는지 없다.
  - 백업 **내보내기** 흐름(읽기 트랜잭션 스냅샷, 임시 파일 후 이름 바꾸기, 공유 경로)이 없다.
- **수정:** §11.1에 JSON 스키마를 필드명·타입·필수 여부까지 적는다. 코드포인트는 5자리 대문자 16진. `index.json`에 음절별 `{selection, current, revisions: [{seq, createdAt}]}`, `seq` = 음절별 `created_at, id` 오름차순 1부터. 삭제 표시된 메모와 초안은 제외한다고 적는다. §11.3 "백업 만들기"를 추가한다: 읽기 트랜잭션 하나 → `<tmp>/x.hwaeaek.part` → 이름 바꾸기 → `share_plus`. 대안은 제안 P-3 참조.

### B-5. 가져오기 검증이 메모리 고갈과 악성 파일을 막지 못한다
- **리뷰어:** implementation-readiness, design, inventive-catalyst
- **위치:** §11.2 436~440행 (RISK-08, TS-18)
- **문제:**
  - `archive` 기본 API(`ZipDecoder().decodeBytes`)는 아카이브 전체를 메모리에 올린다. 압축 해제 총량 1GB 상한으로는 조작된 백업 하나로 iPad를 종료시킬 수 있다. ZIP 헤더의 크기 값은 공격자가 정한다.
  - 의미 검증이 없다. 자모 키가 51자 안인지, 커스텀 코드포인트가 `AC00..D7A3` 안인지(PRD §9는 호환 자모 커스텀을 제외), `selection = custom`이면 현재 수정본 파일이 있는지, `.hws`마다 `.hwo`가 있는지, 좌표가 유한수인지, 필압이 0~1인지, `t`가 줄지 않는지, HWO 컨투어 점이 3개 이상인지, 파싱 후 남는 바이트가 있는지, 메모 길이 상한, 폰트 이름 규칙(name ID 6) 재검사.
  - "점 100,000개"가 획당인지 파일당인지 모호하다.
  - 사용자에게 보일 실패 사유와 문구가 없다. TS-18은 사유를 확인해야 한다.
- **수정:** §11.2를 다시 쓴다.
  - `InputFileStream`으로 항목별로 풀고, 실제로 만들어진 바이트를 세어 상한을 넘는 순간 중단한다. 항목별 상한(`.hws`/`.hwo` ≤ 4MB, JSON ≤ 16MB)과 총량 상한(≤ 512MB 등)을 둔다.
  - 중복 항목 이름, 심볼릭 링크, 암호화 항목, stored/deflate 외 압축 방식을 거부한다. 풀기 전에 중앙 디렉터리 항목 수를 검사한다.
  - 위 의미 검증 목록을 추가하고, 알 수 없는 파일은 거부한다(무시하지 않는다).
  - 실패 코드와 한국어 메시지 표를 둔다.
  - 백업 크기 상한은 만들 때도 같은 기준으로 검사한다(M-29).

## 주요 (Major)

### A. PRD와 맞지 않거나 PRD 요구가 빠진 곳

#### M-1. 원본 획 데이터에 기울기가 없다 — 결정 필요
- **리뷰어:** structural, implementation-readiness, design, zoom-out
- **위치:** §3.1 81·85행, §4.2 181행
- **문제:** PRD 45행은 원본 획 데이터를 "점 좌표·시간·필압·**기울기**"로 정의한다. `InkPoint`와 HWS1에 기울기가 없고, 85행은 시간만 인용한다. HWS1은 디스크와 백업에 남는 형식이라 나중에 추가하면 HWS2와 전체 행 마이그레이션이 필요하다.
- **수정:** `tilt f32`, `orientation f32`(없으면 NaN)를 HWS1에 지금 추가한다. 또는 `[Spec 결정]`으로 빼는 이유를 적고 PRD 용어 정의를 고친다.

#### M-2. FR-08 내보내기 요구가 일부 빠졌다
- **리뷰어:** structural, implementation-readiness, design, zoom-out, comprehension
- **위치:** §7.2 313~325행, §13.1 461~468행, §16 499행
- **문제:**
  - (a) PRD 259행은 "**내보내기 전에** 제외 음절 수와 목록"을 요구한다. Spec은 빌드·파일 쓰기·버전 증가 뒤의 결과 시트(7단계)에서 보여 준다. — 결정 필요
  - (b) PRD 257행의 진행률 표시가 흐름에 없다. isolate 진행 보고 방식이 없다.
  - (c) PRD 266행의 "앱을 삭제하면 iOS가 설치한 폰트도 제거" 안내가 §13.1에 없다.
  - (d) PRD 259행의 "윤곽선 변환에 실패한 커스텀 음절"이 정의되지 않았다(빈 윤곽선, 점 수 > 65,535, i16 범위 밖 좌표 등).
  - (e) "편집을 막는다"가 무엇을 막는지(메모 입력 포함 여부, 모달 경로 등) 없다.
- **수정:** (a) 결과 시트를 "파일 저장·공유·설치 전" 단계로 정의하고 PRD의 "내보내기 전"이 이를 뜻한다고 PRD에 반영하거나, 빌드 결과를 보여 준 뒤 사용자가 확인해야 파일을 쓰도록 흐름을 바꾼다. (b) 500 코드포인트마다 `SendPort`로 진행률 전송. (c) §13.1에 안내 문구 추가. (d) 커스텀 제외 조건 목록 추가. (e) 내보내기 중 모달 장벽, 메모 입력 포함 여부를 적는다.

#### M-3. "NFC"가 실제로는 부분 정규화이고, 입력 중 적용하면 한글 IME가 깨질 수 있다 — 결정 필요
- **리뷰어:** comprehension, implementation-readiness, design, zoom-out
- **위치:** §8.3 365행, §4.1 159행
- **문제:** PRD 237행은 `[확정]` NFC다. Spec은 첫가끝 → 완성형만 한다. 또 `TextInputFormatter`는 IME 조합 중에도 매 편집마다 돈다. 조합 범위 안의 텍스트를 바꾸면 iOS·Android에서 한글 조합이 깨지는 것은 알려진 문제이고, FR-07·TS-11이 여기에 걸려 있다. 첫가끝 범위(`U+1100~U+11FF`)에는 조합할 수 없는 옛한글도 섞여 있다.
- **수정:** `value.composing`이 비어 있을 때(조합 완료·붙여넣기)만 정규화하고 커서 위치를 보정한다. 조합 대상은 현대 L(1100~1112)·V(1161~1175)·T(11A8~11C2)만으로 한정하고 테스트 벡터를 적는다. 완전 NFC가 필요하면 `unorm_dart` 등 패키지를 쓰고, 아니면 PRD를 "한글 범위 정규화"로 고친다. DB 주석의 "NFC"도 같은 용어로 바꾼다. 위젯 테스트: 포매터가 켜진 상태에서 ㄱ→가→강 조합.

#### M-4. 기본 글리프 세트 버전 갱신(POL-07, TS-20)과 메모 잠금 해제 유지(FR-04)가 없다
- **리뷰어:** structural, comprehension, implementation-readiness

#### M-5. 조합 오류 판정이 메모 폰트와 내보내기에서 다르다
- **리뷰어:** codebase-details, implementation-readiness

#### M-6. FR-02 획 지우기·다시 쓰기, FR-05 수정 이력 화면이 정의되지 않았다

### B. "(PoC 유지)" 주장과 코드 불일치

#### M-9. §7.1 `head` created/modified는 PoC에서 고정값이다
- **리뷰어:** codebase-details
- **위치:** §7.1 299행 ("(PoC 유지)" 절)
- **문제:** `FontSpec.created` 기본값은 `DateTime.utc(2026)`(`ttf_writer.dart:37`)이고 두 필드에 같이 쓰인다(`:142-143`). 어떤 호출도 값을 넘기지 않는다(`font_session.dart:177-183, 219-227`). 지금 모든 폰트는 2026-01-01로 찍힌다.
- **수정:** "PoC: 고정값. 제품: 내보내기 시각(UTC)을 넘긴다"로 고치고, `created`를 필수 인자로 바꾼다고 적는다. 메모 폰트는 고정값을 써도 된다고 명시한다.

#### M-10. §7.2 4단계 검증식이 공백 글리프를 빠뜨려 매번 실패한다
- **리뷰어:** codebase-details, implementation-readiness, comprehension, design
- **위치:** §7.2 316~317행
- **문제:** 빌더는 항상 공백(U+0020)을 넣는다(`ttf_writer.dart:91`). cmap 항목 = 유효 글리프 + 1, `numGlyphs` = 유효 글리프 + 2다. PoC 테스트도 `11172 + 51 + 1`을 기대한다(`composer_test.dart:80`). Spec 문구대로 구현하면 모든 내보내기가 검증에서 실패한다. 3단계에도 공백이 없다.

#### M-11. §6.3이 인용한 결정성 테스트는 규칙 v1을 검증하지 않는다
- **리뷰어:** codebase-details

#### M-12. §6.3: 플랫폼 간 결과가 다르면 PRD FR-04를 약화하겠다는 대비책 — 결정 필요
- **리뷰어:** inventive-catalyst, design
- **위치:** §6.3 276행, §16 500행

#### M-13. `ruleVersion`의 범위와 쓰임이 정의되지 않았다
- **리뷰어:** comprehension, design, inventive-catalyst, codebase-details
- **위치:** §6.1 244행, §6.2 271행, §5 222행, §3.1 83행
- **문제:**
  - 자동 생성 음절은 `ComposerMetrics`만이 아니라 펜 파이프라인 전체에 달려 있다. `StrokeOptions`는 size·thinning·smoothing·simulatePressure·isComplete만 넘기고(`ink.dart:52-58`) 나머지(`streamline` 0.5, easing, cap, taper)는 `perfect_freehand`의 **변경 가능한 정적 기본값**에 기댄다(`stroke_options.dart:6-12, 165-166`). 패키지 업데이트나 §5의 `streamline` 조정(OQ-08)이 `ruleVersion` 변경 없이 11,223자를 모두 바꾼다.
  - `ruleVersion`은 프로젝트·스냅샷·백업 어디에도 저장되지 않아, 무엇이 읽고 올리면 무슨 일이 생기는지 알 수 없다. POL-08/OQ-12(즉시 적용 / 승인 후 적용)를 나중에 구현하려면 마이그레이션이 필요하다.
  - PoC의 규칙 버전은 `CompositionRule` enum(`composer.dart:28-35`)에 있고 `static const ruleVersion`은 새 코드다.
- **수정:** `ruleVersion` = 조합 값 + 펜 파이프라인(라이브러리 버전, 모든 `StrokeOptions` 값, 단순화, 반올림) 전체의 버전으로 정의한다. `PenStyle`에 `streamline`·cap·taper를 넣고 명시적으로 넘긴다. `perfect_freehand`를 정확한 버전으로 고정한다. `projects.rule_version`과 백업 manifest 필드를 추가한다. M-11 해시 골든이 `ruleVersion` 변경 없이 바뀌면 CI가 실패하게 한다.

#### M-14. §1.2·§6.1이 조합기 재작성 규모를 낮춰 적었다

### C. 저장소·데이터 무결성

#### M-17. `drafts` 테이블이 스키마 밖에 있다
- **리뷰어:** 8명 중 7명(structural, comprehension, implementation-readiness, design, zoom-out, style, inventive-catalyst)
- **위치:** §4.4 213행, §4.1, §3.2, §11.1, §12
- **문제:** DDL·기본 키·FK·CASCADE가 없고, `target`이 문자열 합성 키(`base:ㄱ`/`custom:44032`)다. `schemaVersion` 1·마이그레이션 픽스처·백업 포함 여부·테스트에 없다. 언제 다시 쓰는지(획 완료·지우기·Undo·Redo)도 없다.
- **수정:**
  ```sql
  CREATE TABLE drafts (
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    kind TEXT NOT NULL CHECK (kind IN ('base', 'custom')),
    key TEXT NOT NULL,                   -- 자모 또는 코드포인트 10진
    strokes BLOB NOT NULL,               -- HWS1, 화면에 보이는 획 전체

    PRIMARY KEY (project_id, kind, key)
  );
  ```

- **위치:** §4.1 148~154·167행, §3.3 108행
- **문제:** `REFERENCES custom_revisions(id)`는 "어떤 수정본이 있다"만 보장한다. "수정본 지정"이나 실행 취소 버그로 `강`이 `각`의 수정본이나 다른 프로젝트 수정본을 가리켜도 DB가 받아들인다. 167행 "DB 수준에서 성립한다"는 과장이다. 스냅샷 검사가 실패하면 무엇을 하는지도 없다.
- **수정:** `custom_revisions`에 `UNIQUE(project_id, code_point, id)`, `custom_glyphs`에 `FOREIGN KEY (project_id, code_point, current_revision_id) REFERENCES custom_revisions(project_id, code_point, id)`. 두 테이블에 `CHECK (code_point BETWEEN 44032 AND 55203)`. 스냅샷 검사 실패 시 동작(오류 상태 표시, 내보내기 거부)을 정한다. `foreign_keys = ON`은 모든 연결의 `beforeOpen`에서 켠다고 적는다.

#### M-19. 내보내기 파일·버전 증가가 원자적이지 않다
- **리뷰어:** design, implementation-readiness, inventive-catalyst, comprehension, codebase-details
- **위치:** §7.2 318~319·323~324행, §4.1 126행, §3.2 92행
- **문제:**
  - 파일을 쓴 뒤 6단계(DB 증가)가 실패하거나 그 사이에 앱이 죽으면 다음 내보내기가 같은 `fontRevision`과 같은 파일 이름을 쓴다. TS-13과 OQ-09/TS-M4의 같은 버전 재설치 캐시 문제가 생긴다.
  - 파일에 넣는 버전이 증가 전 값인지 후 값인지 모호하다. `versionMinor ≥ 1000`이면 `fontRevision` 2.000이 되고 `versionString`의 padLeft(3)도 깨진다(`ttf_writer.dart:59-60, 137`).
  - 4단계는 메모리 바이트를 검증하고 디스크의 파일은 검증하지 않는다.
  - `exports/<asciiName>-v<minor>.ttf`는 프로젝트 간 충돌할 수 있다(`asciiName`은 사용자가 바꿀 수 있고 유일하지 않다). 내보낸 파일(약 7.4MB)이 계속 쌓인다.
  - "isolate가 중단되면"을 감지할 방법이 없다. iOS는 대개 죽이지 않고 일시 정지한다.
- **수정:** 순서를 "`minor + 1`로 빌드 → `<최종>.part`에 쓰기 → 디스크에서 다시 읽어 검증 → DB에 `minor + 1` 커밋 → 이름 바꾸기"로 바꾼다. 커밋 뒤에 죽으면 버전 번호만 건너뛰며 POL-06상 무해하다. 경로는 `exports/<projectId>/<asciiFamilyName>-v<n>.ttf`, 최근 N개만 보관(설치된 파일 제외), 시작 시 `.part` 정리. 999 다음 동작을 정한다. `AppLifecycleState.paused`에서 `Isolate.kill` 후 폐기, 또는 iOS `beginBackgroundTask`로 유예 시간 안에 끝내고 만료 시에만 폐기한다.

#### M-20. 기본 글리프 키가 위치 변형을 표현할 수 없다
- **리뷰어:** implementation-readiness, zoom-out
- **위치:** §3.2 93행, §4.1 130~136행, §6.1 243행, §11.1 429행
- **문제:** PRD는 "`ㄱ`(초성)"처럼 역할로 이름 붙이고(TS-01, PRD §5), FR-03/OQ-01은 위치 변형을 계획한다. 키가 자모 1자면 나중에 변형을 넣을 때 기본 키 마이그레이션과 백업 형식 변경이 필요하다. 지금 키로는 TS-01 기대 결과("`ㄱ`(초성)을 쓰는 음절만")가 모호하다. `dependencies()` 키 문법도 정의되지 않았다.
- **수정:** 열을 불투명 문자열 `role_key`로 바꾸고 문법을 정한다(현재 `ㄱ`, 이후 `ㄱ@cho.h` 등). 백업 파일 이름과 `dependencies()`가 같은 문자열을 쓴다. TS-01 기대 집합을 `{cp | 'ㄱ' ∈ dependencies(cp)}`로 명시한다.

#### M-21. 커스텀 음절을 편집 펜(64)으로 굳히면 자동 생성 음절보다 굵다 — 결정 필요
- **리뷰어:** design, implementation-readiness
- **위치:** §3.1 83행, §3.2 94행
- **문제:** 커스텀 윤곽선은 편집 펜(64)으로 만들어 영구 저장한다. 자동 생성 음절은 56에 `s^0.35` 축소를 곱한다. 메모에서 커스텀 음절만 눈에 띄게 굵어질 수 있고, 윤곽선이 고정되므로 나중에 고칠 수 없다. 어떤 펜을 쓰는지도 Spec에 적혀 있지 않다.
- **수정:** 첫 릴리스 전에 커스텀 음절 펜을 정한다(예: 조합 펜 56, 배율 1). OQ-02 펜 조정과 함께 결정한다. `custom_revisions`에 펜 매개변수를 기록한다.

### D. 상태·동적 폰트·성능

#### M-22. 메모 폰트 무효화가 비동기 스냅샷과 경쟁하고, 실패 시 재시도하지 않는다
- **리뷰어:** design, implementation-readiness, comprehension
- **위치:** §8.1 342~357행, §9.3 394~396행
- **문제:**
  - `dirty`는 저장 "이벤트"로 켜지지만 스냅샷·조합기는 Drift 스트림으로 비동기 갱신된다. 스트림보다 먼저 다시 빌드하면 옛 스냅샷으로 빌드하고 `dirty`는 꺼져서, 편집에서 돌아와도 옛 모양이 남는다(FR-07, TS-10 실패).
  - 의사 코드가 빌드 성공 전에 `dirty = false`, `loaded ∪=`를 하므로 빌드나 `FontLoader`가 실패하면 다시 시도하지 않는다.
  - 텍스트 변화 없이 `dirty`만 바뀔 때 누가 `ensureFontFor`를 부르는지 없다.
  - `dirty` 계기 목록에 커스텀 삭제가 없다.
  - 새 폰트 등록 전 새 글자는 §8.2 규칙상 "유효 글리프 없음" 색으로 깜빡인다.
- **수정:** `ProjectSnapshot`에 단조 증가 `revision`을 둔다. 메모 폰트는 `builtFromRevision`을 기록하고 `snapshot.revision != builtFromRevision || !loaded.containsAll(needed)`이면 다시 빌드한다. `load()` 성공 후에만 `loaded`·`applied`를 갱신한다. `memoFontProvider`가 `snapshotProvider`를 구독해 스스로 다시 빌드한다. `dirty` 계기를 "`effectiveGlyph`를 바꿀 수 있는 모든 쓰기(§4.3 2~5행)"로 정의한다. §8.2 대체 색은 "조합 오류로 알려진 글자와 비한글"에만 쓰고 등록 대기 중인 글자에는 쓰지 않는다. 판정은 `loaded`가 아니라 **적용된 세대의 cmap** 기준이다.

#### M-23. 동적 폰트 이름이 다시 쓰일 수 있다
- **리뷰어:** implementation-readiness, design
- **위치:** §8.1 342·350행
- **문제:** `generation`이 `memoFontProvider(id)` 상태에 있다. provider가 autoDispose되거나 프로젝트를 다시 열면 1부터 다시 세어 `hw_<id8>_1`을 다시 등록한다. Spec이 피하겠다는 바로 그 같은 이름 캐시 문제다(PRD 358행). PoC 이름은 `hw_<gen>`이고 projectId 부분은 새로 추가한 것이다.
- **수정:** 프로세스 전역 단조 증가 카운터(정적 변수 또는 해제되지 않는 최상위 provider)를 쓴다. 메모 폰트 빌드가 어느 isolate에서 도는지도 적는다(PoC는 UI isolate에서 동기 실행).

#### M-24. 필수 글리프 순서의 "처음 10자 미리보기"가 성립하지 않는다 — 결정 필요
- **리뷰어:** comprehension, zoom-out, style
- **위치:** §10 416행
- **문제:** 순서상 처음 10자는 `ㄱ~ㅊ` 자음뿐이라 어떤 음절도 조합할 수 없다(§6.2 5단계). PRD 162·234행은 조합·메모를 필수 글리프를 다 쓴 뒤로 둔다. 따라서 미리보기는 PRD에 없는 새 범위다.
- **수정:** 미리보기 문구를 빼거나, 자음과 모음을 섞은 순서(예: `ㄱ ㄴ ㅇ ㅏ ㅓ ㅗ ㅜ ㅡ ㅣ …`)로 바꾸고 무엇을 미리 보여 주는지 정해 PRD에 반영한다.

#### M-25. 스냅샷·조합기 provider 구성이 §6.5 선택적 무효화를 무력화한다
- **리뷰어:** design, zoom-out, implementation-readiness, inventive-catalyst
- **위치:** §6.5 285~289행, §9.3 394~395행
- **문제:** `composerProvider`가 `snapshotProvider`에서 파생되므로, 커스텀 저장·선택 변경·(테이블을 거르지 않으면) 초안·메모 쓰기마다 새 스냅샷 → 새 조합기 → 빈 캐시가 된다. §6.5의 "의존 항목만 버린다"는 실행될 기회가 없다. 스냅샷을 다시 만들 때마다 모든 기본·커스텀 BLOB을 다시 디코딩한다.
- **수정:** 프로젝트당 수명이 긴 조합기·캐시를 둔다. 스트림은 `base_glyphs`, `custom_glyphs`, `custom_revisions`, `projects`만 구독한다. 기본 글리프 `updated_at`을 비교해 바뀐 자모에만 `invalidate(j)`를 부른다. 스냅샷을 기본 글리프 부분과 커스텀·선택 부분으로 나눈다. 단순화가 우선이면(zoom-out 의견) "기본 글리프가 바뀌면 캐시 전체를 버린다"로 하고 `dependencies()`는 OQ-01 산출물로만 둔다. 어느 쪽이든 하나로 정한다.

#### M-26. 미리 담기 때문에 편집마다 전체 메모 글자를 다시 빌드하고, 등록 폰트가 메모리에 쌓인다
- **리뷰어:** design, inventive-catalyst
- **위치:** §8.1 354~357행, §6.5 287행
- **문제:** 모든 메모 글자를 `loaded`에 넣으면 1~2천 음절이 될 수 있다. 이후 새 글자 하나, 글리프 편집 하나마다 그 전체를 UI isolate에서 다시 조합·빌드·등록한다. 등록 폰트는 해제할 수 없으므로 빌드마다 0.5~1MB씩 쌓인다. 354행 "글자 수십~수백 개짜리라 메모리 영향은 작다"는 미리 담기와 맞지 않는다. 조합 캐시에도 상한이 없다.
- **수정:** 메모 폰트를 층으로 나눈다(제안 P-2): 프로젝트를 열 때 한 번 만드는 기본 폰트, 새로 입력한 글자만 담는 작은 증분 폰트, 마지막 편집으로 바뀐 코드포인트만 담는 덮어쓰기 폰트를 `fontFamily` + `fontFamilyFallback`으로 잇는다. 임계값이나 유휴 시 합친다. 기본 폰트 빌드는 백그라운드 isolate에서 한다. 조합 캐시에 LRU 상한을 둔다. OQ-11 iPad 측정 항목에 "세션당 등록 폰트 바이트"를 추가한다.

#### M-27. 빈도순 목록·편집 가이드의 음절 렌더링 방법이 없다
- **리뷰어:** implementation-readiness, design

- **문제:** 11,172칸 격자를 메모 동적 폰트로 그리면 `loaded`가 전체 집합이 되어 M-26이 최악이 된다. 윤곽선을 직접 그리면 무제한 캐시를 채운다.
- **수정:** "목록은 `CustomPainter`로 조합기 윤곽선을 직접 그린다. `SliverGrid`로 보이는 칸만 지연 조합, 고정 크기 LRU `Path` 캐시. 메모 폰트와 분리"를 적는다.

#### M-28. 손바닥 방지 규칙이 Pencil을 막는다

### E. 백업·플랫폼

#### M-29. 백업 크기 상한이 무제한 수정 이력과 맞지 않는다
- **리뷰어:** design, inventive-catalyst
- **위치:** §11.2 436행
- **문제:** PRD는 수정 이력을 무제한 보관한다. 오래 쓴 프로젝트는 가져오기 상한(200MB / 100,000항목)을 넘는 백업을 만들 수 있고, 사용자는 복원할 수 없는 백업을 갖게 된다(RISK-03이 막으려는 데이터 손실). `archive`로 메모리에서 ZIP을 만드는 것도 큰 메모리 사용이다.
- **수정:** 만들 때 같은 상한을 검사해 경고·거부한다. 또는 상한을 현실적 최악값(예: 11,172 × K 수정본 × 10KB)에서 도출한다. 쓰기·읽기 모두 스트리밍한다. manifest에 `ruleVersion`, `baseSetVersion`을 기록한다.

#### M-30. Android "기기에 저장"과 가져오기 파일 선택 경로가 없다
- **리뷰어:** design
- **위치:** §13.2 472행, §10 406행
- **문제:** FR-08은 TTF를 기기에 저장, FR-09는 백업 파일 가져오기를 요구한다. Android 공유 시트에는 믿을 만한 "파일에 저장" 대상이 없고, 가져오기 파일 선택 방법이 Spec에 없다. tech-stack.md는 `file_picker`를 언급하지만 Spec은 빠뜨렸다.
- **수정:** `file_picker`(또는 SAF `CREATE_DOCUMENT`/`OPEN_DOCUMENT`)로 Android 저장과 양 플랫폼 가져오기를 정의한다.

#### M-31. iOS 폰트 설치에 안정적인 파일 경로가 없다
- **리뷰어:** implementation-readiness, zoom-out
- **위치:** §13.1 465~468행
- **문제:** `.persistent` 등록은 URL의 파일이 계속 있어야 할 수 있는데, 내보내기 파일은 버전마다 이름이 바뀌고 보관 정책이 없다(M-19 정리와 충돌). "같은 이름이면 먼저 해제"를 어떻게 감지하는지 없다. `uninstall`은 PRD가 요구하지 않는다.
- **수정:** `<Application Support>/installed/<psName>.ttf`에 복사하고 그 URL로 해제 후 등록한다. 비동기 완료를 `ok/denied/error`에 대응시킨다. iOS가 복사하는지 참조하는지 G0에서 확인한다고 §16에 넣는다. `uninstall`은 install 안으로 넣고 채널에서 뺀다. Android에서는 버튼을 숨긴다.

#### M-32. OS 기기 백업: Android 25MB 한도, WAL 파일
- **리뷰어:** implementation-readiness, design
- **위치:** §13.3 476행
- **문제:** Android Auto Backup은 앱당 25MB 한도라 큰 프로젝트는 조용히 백업이 멈춘다(NFR-04). WAL 모드 DB는 파일 3개로 백업되어 원자적이지 않다. 문단이 "exports 포함"이라 했다가 바로 제외한다.
- **수정:** `allowBackup`, `dataExtractionRules` 규칙과 한도 초과 동작을 적거나 알려진 한계로 기록한다. 백그라운드 전환 시 `wal_checkpoint(TRUNCATE)`. 문단을 "DB는 포함, `exports/`는 제외"로 고친다.

### F. 테스트·문서 구조

#### M-33. 테스트 계획 중 실제로 쓸 수 없거나 조용히 건너뛰는 것이 있다
- **리뷰어:** implementation-readiness, codebase-details, comprehension
- **위치:** §12 446~457행, §7.3 329행
- **문제:**
  - CI 설명에 `tools/validate_ttf.py` 실행이 없다. PoC 테스트는 `.venv-tools`가 없으면 `markTestSkipped`(`ttf_writer_test.dart:61-63`)하거나 그냥 `return`해서 통과한다(`composer_test.dart:74,126`). 상대 경로라 작업 디렉터리가 `app/`이어야 한다.
  - TS-02(재시작)는 메모리 DB로 흉내 낼 수 없다. TS-15·16은 오류 주입, TS-14는 isolate 강제 종료, TS-11은 IME 조합 범위 입력이 필요하다.

## 제안 (선택 사항, 설계 대안)

결함이 아니라 같은 PRD 제약 안에서 여러 비용을 한꺼번에 줄일 수 있는 대안이다. 채택 여부는 작성자 판단이다.

### P-1. 자모 composite 글리프로 파일 크기·내보내기 시간·메모 폰트 비용을 함께 줄이기 (§6.2, §7.1, §7.4)
- **리뷰어:** inventive-catalyst
- 규칙 v1은 자모를 자기 획과 자리만으로 맞추고, 펜 지름도 그 자모의 축소율에만 달려 있다. 따라서 (자모, 자리) 쌍의 윤곽선은 그 자리를 쓰는 모든 음절에서 같다. 자리 수는 유한하다(레이아웃 6 + 꼬리 높이기 + 겹자음 반쪽 자리).
- §7.4가 composite를 보류한 이유(배율로 굵기가 바뀜, 합칠 수 없음)는 v1에 해당하지 않는다. 항등 변환이면 굵기가 그대로이고, 겹침은 이미 OVERLAP_SIMPLE로 받아들이고 있으니 OVERLAP_COMPOUND도 같은 위험이다.
- `placeJamo(jamo, slotId)` 메모(수백 개) + `compose(cp)` 조립으로 나누면 다시 입히기가 11,172번에서 수백 번으로 줄고, 파일 크기가 크게 줄 것으로 예상된다. TS-12는 분해한 윤곽선으로 비교한다.
- 대가: `ttf_writer`의 composite 지원(`maxComponentElements`/`Depth`), §7.3 리더, DirectWrite/GDI·Core Text 겹침 확인(TS-M1). §16 OQ-03 파일 크기 행에 이 영향을 적어야 한다.

### P-2. 메모 동적 폰트를 기본·증분·덮어쓰기 층으로 나누기 (§8.1)
- **리뷰어:** inventive-catalyst, design
- M-26 수정안의 상세. 편집 한 번의 다시 빌드·누수 비용이 O(loaded)에서 O(바뀐 글자)로 준다. 대가: 등록 횟수 증가, 대체 체인 조회 비용(iPad 측정), 합치기 로직, §8.2 판정은 층의 합집합 기준.

### P-3. 백업을 프로젝트 행만 담은 SQLite 파일로 (§11)
- **리뷰어:** zoom-out, inventive-catalyst
- ZIP 안에 `manifest.json` + `VACUUM INTO`/`ATTACH`로 만든 프로젝트 단위 SQLite 파일 하나를 둔다. 가져오기는 읽기 전용으로 열고 `PRAGMA trusted_schema=OFF`, `integrity_check`, 같은 Drift 마이그레이션, HWS1/HWO1 검사 후 새 ID로 한 트랜잭션 복사. `formatVersion`과 `schemaVersion` 두 이주 경로가 하나로 준다(B-4의 형식 정의 부담도 줄어든다).
- 대가: 신뢰할 수 없는 SQLite 파일 파싱이라는 공격 면(강화 pragma와 크기 상한 필요), 사람이 읽을 수 없음.

### P-4. 프로젝트당 장수 조합 워커 isolate (§6.5, §7.2, §9.3)
- **리뷰어:** inventive-catalyst
- 조합기·캐시·P-1 메모를 가진 워커 하나가 `compose`, 메모 폰트 빌드, 내보내기를 모두 처리한다. UI는 변경분만 보낸다. 내보내기가 따뜻한 캐시를 버리고 처음부터 다시 계산하는 낭비가 사라진다. 대가: 메시지 비용, 워커 수명 관리(백그라운드에서 죽으면 DB에서 재구성), 변경분 버전 관리.
