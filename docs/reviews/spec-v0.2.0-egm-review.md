1. **§20 단계 1이 빌드 가능한 상태로 끝날 수 없다**(B-6). §6.2의 "(PoC 동작 유지)" 표시는 실제와 다르다(R-1).

## 2. 구현 1~2단계 전에 고칠 것

### B-6. §20 단계 1이 빌드 가능한 상태로 끝날 수 없고, 단계별 파일·도구 결정이 없다 — 차단
- **리뷰어:** implementation-readiness, codebase-details
- **위치:** §20 841~852행, §1.2 60~79행, §15 744~759행
- **문제:**
  - 단계 1은 조합기를 획 전용으로 바꾸고 PoC `BaseGlyph`를 없앤다. 그런데 `app/lib/app/font_session.dart`, `memo_screen.dart`, `base_glyph_screen.dart`, `glyph_painter.dart`, `app/lib/dev/fixture_glyphs.dart`, `app/lib/main.dart`가 모두 `composer.dart`나 `glyph.dart`를 가져온다. 이 파일들을 단계 1에서 고치는지 지우는지 없다. "각 단계는 빌드와 테스트가 통과하는 상태로 끝난다"(839행)를 지킬 수 없다.
  - 테스트 파일이 빠졌다.
    - `app/test/hangul/pen_scale_experiment_test.dart`는 "유지"(757행)라 되어 있지만 `HangulComposer(Map<String, BaseGlyph>, metrics: ComposerMetrics(...))`를 부른다(`:25-28`). §6.1 시그니처와 다르다. `ComposerMetrics`(`composer.dart:86-130`)는 Spec 어디에도 없다.
    - `composer_test.dart`는 v0 윤곽선 픽스처를 쓴다. `ttf_writer_test.dart`는 PoC 경로를 가져온다. 두 파일 모두 처리 방침이 없다.
  - 단계 범위가 `app/lib/domain/**` 같은 glob이다. 다음 파일이 목록에 없다: `pubspec.yaml`, 골든 파일, DB 픽스처, 오류 주입 래퍼, CI 설정, import 검사 스크립트.
  - 852행은 패키지 버전을 "단계 시작 시 고정"으로 미룬다. 다음도 정하지 않았다.
    - Riverpod 2와 3 중 무엇을 쓰는지, 코드 생성을 쓰는지
    - Drift 스키마를 Dart 클래스로 쓰는지 `.drift`로 쓰는지. §4.1의 복합 FK, `_guard`, 트리거는 `.drift`/raw SQL이 자연스럽다.
- **수정:**
  - 단계별로 만들 파일·고칠 파일·지울 파일 목록을 둔다. 테스트와 Drift 생성 파일도 넣는다.
  - 단계 1에서 PoC UI를 어떻게 처리할지 정한다. 예: `app/lib/app/*`과 `main.dart`를 단계 1에서 지우고, 단계 4까지 `main_dev.dart`만 남긴다.
  - `ComposerMetrics`를 남길지 정하고, 남기면 `metrics.dart`와의 관계를 적는다.
  - 패키지 정확한 버전, Riverpod 방식, Drift 스키마 형식을 지금 정한다.

### R-1. §6.2 "(PoC 동작 유지)"가 사실과 다르고, 오류 판정을 지금 구조로는 구현할 수 없다 — 주요
- **리뷰어:** codebase-details, design, implementation-readiness, style
- **위치:** §6.2 357·410·412·414행
- **문제:** 아래 세 곳은 골든 해시와 TTF 바이트를 바꾸므로 구현자가 PoC를 그대로 옮기면 안 된다.
  - **컨투어 순서:** Spec은 "`d`가 큰 묶음부터"다. PoC는 묶음을 처음 나온 순서로 돌며 새 묶음을 앞에 붙인다(`composer.dart:189-199`, `glyph.dart:72-73`). 결과는 처음 나온 순서의 역순이다. 묶음 안 획 순서도 정의되지 않았다(PoC는 배치 순서, `:233-240`).
  - **단독 호환 자모:** Spec은 56 펜이다. PoC는 64 펜으로 만든 `base.outline`을 그대로 돌려준다(`composer.dart:163-164`, `ink.dart:25`).
  - **오류 판정:** Spec은 "넣은 자모 중 하나라도 윤곽선이 비면 null"이다(414행). 하지만 7단계는 여러 자모의 획을 펜 지름별로 섞어 한 번에 윤곽선으로 만든다. 그래서 특정 자모의 윤곽선이 비었는지 알 수 없다. PoC는 해당 자모를 건너뛴다(`:225-226`).
- **수정:**
  - 제목을 "(PoC 변경: 컨투어 순서, 단독 자모 펜, 오류 판정)"으로 바꾼다.
  - 묶음 순서와 묶음 안 순서를 명시한다.
  - 오류 판정을 정의한다. 예: 자모마다 `strokesToOutline`을 먼저 시험해 비면 null로 처리하거나, "그 자모의 모든 획이 단순화 후 3점 미만 컨투어만 남기면 오류"로 정의한다.

### R-2. 크기가 1단위 미만인 기본 글리프가 조합을 NaN으로 망가뜨린다 — 주요
- **리뷰어:** design (합성자가 `composer.dart:317-328`에서 확인)
- **위치:** §6.2 6단계 402~407행, 414행, §7.2 483행
- **문제:**
  - 점 하나나 아주 작은 점처럼 가로·세로 범위가 모두 1 미만이면 `scaleX`와 `scaleY`가 둘 다 ∞로 남는다. 그러면 `gw*scaleX` = 0·∞ = NaN이 되고, 정수 반올림에서 예외가 난다.
  - 414행의 저장 차단은 빈 획만 막으므로 이런 글리프는 저장된다.
  - 결과: UI isolate의 메모 폰트 빌드가 예외로 끝난다. 내보내기는 "조합 isolate 오류"로 전체 실패한다. FR-08은 해당 음절만 빼고 내보내기를 끝내라고 요구한다.
- **수정:**
  - 두 축이 모두 퇴화하면 조합 오류(null)로 정의한다.
  - 저장 시 최소 범위를 검사한다.
  - `compose`가 글자별 예외를 잡아 null로 바꾼다고 적는다.
  - 점 하나짜리 기본 글리프 단위 테스트를 추가한다.

### R-3. f32 양자화 위치와 펜 입력이 아닌 점의 `t`가 정해지지 않았다 — 주요
- **리뷰어:** codebase-details
- **위치:** §3.1 109행, §5 323행
- **문제:**
  - "생성 즉시 양자화"라고만 되어 있다. 조합기도 배치할 때 새 `InkPoint`를 만든다(`composer.dart:236-238`). 양자화를 생성자에 넣으면 조합 결과와 골든이 바뀐다. 입력 계층에만 넣으면 개발용 획 픽스처는 양자화되지 않는다.
  - 픽스처 점(`stroke_fixture.dart:212-221`)에는 필수 `int t`의 출처가 없다.
- **수정:**
  - 양자화는 "입력 계층과 HWS1 디코더에서만 한다. 조합기 내부 변환 점은 double을 유지한다" 식으로 한 곳을 정한다.
  - 픽스처와 변환 점의 `t` 값(예: 0 또는 인덱스)을 적는다.

### R-4. `PenStyle`에 easing이 없어 "정적 기본값에 기대지 않는다"가 성립하지 않는다 — 주요
- **리뷰어:** codebase-details
- **위치:** §3.1 111·115~119행, §5.1 334행
- **문제:**

### R-5. 해시 골든이 정의되지 않았고, Spec이 인정한 플랫폼 차이 때문에 CI가 흔들릴 수 있다 — 주요
- **리뷰어:** design, implementation-readiness, codebase-details
- **위치:** §6.3 421·423행, §12 699·711행
- **문제:**

- **수정:**
  - 알고리즘, 대상 바이트, 경로를 명시한다.
  - 골든을 "CI 호스트 한 종류에서만 비교"로 고정하거나 플랫폼별 골든을 둔다.

### R-7. "큐가 비었다"가 정의되지 않아 메모 재시도가 글리프 저장·내보내기·백업을 막는다 — 주요

### R-9. 스냅샷 `revision`을 누가 매기는지 정의되지 않았다 — 주요

  - `updated_at`을 언제 갱신하는지 적는다.
  - 열을 추가하므로 단계 2의 스키마에 들어가야 한다.

### R-13. 백업 만들기 상한과 가져오기 상한이 맞지 않고, 입력 상한이 없다 — 주요, 결정 필요
- **리뷰어:** 합성자 (M-29 후속)
- **위치:** §11.2 668행, §11.3 673~681행, §4.2 257~259행, §5
- **문제:**
  - §11.2 4단계는 "만든 파일이 §11.3 상한을 넘으면"이라고만 한다. §11.3에는 상한이 여러 개다: 파일 512MB, 항목 50,000, `.hws`·`.hwo` 4MB, JSON 16MB, 메모 1MB, 총 1GB. 파일 크기만 보면 다음 백업도 정상 생성된다.
    - `.hws` 하나가 4MB(점 약 17만 개)를 넘는 백업. HWS1은 1000획 × 20,000점 = 2천만 점(480MB)을 허용하고, 편집기에는 상한이 없다.
    - 메모 하나가 1MB를 넘거나 `memos.json`이 16MB를 넘는 백업. 앱에는 메모 길이 상한이 없다.
    - 수정본이 약 2만 5천 개를 넘어 항목이 50,000개를 넘는 백업. 이력은 무제한이다.
  - 이런 백업은 만들 수 있지만 복원할 수 없다(RISK-03).
- **수정:**
  - 입력 단계에 상한을 둔다: 글리프당 획 수, 획당 점 수, 글리프 전체 점 수, 메모 길이. HWS1 상한과 백업 항목 상한이 그 안에 들어가게 맞춘다.
  - §11.2 4단계를 "§11.3의 모든 상한(항목 수, 항목별 크기, 총량, 메모 길이)을 같은 코드로 검사"로 바꾼다.
  - 사용자에게 보이는 상한으로 둘지는 결정 사항이다.

### R-15. 메모 폰트 비용이 메모 크기에 따라 커지는 문제의 측정·전환 기준이 없고, PRD RISK-07 완화책과 다르다 — 주요 (OQ-11)

## 부록 A. 범위 밖으로 둔 의견

- **확정 결정 재논의 (제외):**
  - inventive-catalyst는 메모 폰트를 기본층(KS X 1001)과 증분층으로 나누자고 했다(P-2 계열). 확정된 "열린 메모 범위"와 "P-1~P-4 보류"에 해당하므로 R-15에 측정 항목과 전환 기준으로만 반영했다.
  - design은 커스텀 펜을 음절별 조합 펜에 맞추자고 했다. 확정된 "커스텀 펜 = 56"에 해당하므로 N-9에 표현 문제로만 남겼다.
- **선택적 단순화 제안 (작성자 판단):**
  - zoom-out: 별도 쓰기 큐 대신 Drift 직렬화 활용(R-7 참고).
  - zoom-out: `_guard`·트리거를 빼고 단일 DAO와 행 수 회귀 테스트로 대체. §17 "테스트로 증명할 수 없음" 문구는 §12 700행과 충돌하므로, 유지한다면 근거를 "테스트하지 않은 경로까지 DB가 막는다"로 고친다.
  - zoom-out: §6.2·§7.1의 수치를 코드와 해시 골든에 맡겨 Spec과 코드가 따로 움직이는 위험을 줄이기.
  - zoom-out: `exports/` 최근 3개 보관의 목적이 적혀 있지 않음.

## 부록 B. 확인한 사항

- **DDL:**
  - 복합 FK의 부모 키 `(project_id, code_point, id)`에 `UNIQUE`가 있어 SQLite 요건을 만족한다.
  - 커스텀 삭제 순서는 `custom_glyphs` → `custom_revisions` 이며 NO ACTION FK와 충돌하지 않는다.
  - 프로젝트 삭제 때 CASCADE 삭제도 `custom_revisions` 트리거를 발동한다. 삭제 DAO가 가드를 켜므로 문제없다. `_guard` 행이 없는 경우만 N-1.
  - `CHECK` 범위 44032~55203과 `font_version_minor` 0~999는 맞다.
- **실행 취소:** 비교 후 교체 SQL과 첫 저장 특례(`generated`로, 수정본 유지)가 FK·NOT NULL과 맞는다.
- **내보내기:** `.part` → 검증 → 커밋 → 이름 바꾸기 순서와 실패 시 버전 유지가 POL-05·06을 만족한다.
